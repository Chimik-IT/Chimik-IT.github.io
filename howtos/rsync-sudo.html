The problem

Any sane server has PermitRootLogin no in sshd_config. You log in as your own user and use sudo for anything privileged. That works fine interactively, but falls apart as soon as you want to copy files that only root can read or write: /etc, container volumes under /var/lib, a database dump directory owned by postgres, a backup that has to keep ownership and permissions intact.

The naive attempt: 

rsync -a admin@server:/etc/ ./backup/etc/

ends in a wall of Permission denied for /etc/shadow, /etc/ssl/private and friends. rsync on the other side runs as admin, so it can only see what admin can see.

What --rsync-path actually does

When you rsync over SSH, your local rsync doesn't talk to a daemon. It opens an SSH connection and starts a second rsync process on the remote host, roughly like this: 

ssh admin@server rsync --server --sender -logDtpre.iLsfxCIvu . /etc/

The two processes then speak the rsync protocol over the SSH channel's stdin/stdout. --rsync-path replaces the word rsync in that remote command line. From the manpage: "Use this to specify what program is to be run on the remote machine to start-up rsync."

So with 

rsync -a --rsync-path="sudo rsync" admin@server:/etc/ ./backup/etc/

the remote side becomes sudo rsync --server .... You log in as admin, but the process that reads (or writes) the files runs as root. Root login stays disabled, your SSH key stays personal, and the audit trail in /var/log/auth.log shows who ran what.

It works in both directions. Pulling from the server (remote side is the sender) and pushing to it (remote side is the receiver) both run the remote half through sudo.

The catch: sudo can't ask for a password

The remote rsync's stdin and stdout are the protocol channel. There's no terminal, so sudo has nowhere to prompt. You'll see one of: 

sudo: a terminal is required to read the password; either use the -S option to read from standard input or configure an askpass helper
sudo: a password is required
rsync: connection unexpectedly closed (0 bytes received so far) [Receiver]

The fix is a NOPASSWD rule scoped to rsync. Always edit with visudo, and prefer a drop-in file: 

sudo visudo -f /etc/sudoers.d/rsync

admin ALL=(root) NOPASSWD: /usr/bin/rsync

Check the path with command -v rsync on the server; sudoers matches the full path. Then use sudo -n in the rsync path. -n makes sudo fail immediately instead of hanging if the rule doesn't match, which saves you a lot of head-scratching over a silently stuck transfer: 

rsync -a --rsync-path="sudo -n rsync" admin@server:/etc/ ./backup/etc/

Be honest about what you just granted

NOPASSWD: /usr/bin/rsync looks narrow. It isn't. rsync as root with arguments you choose can overwrite any file on the system: 

rsync --rsync-path="sudo rsync" ./my_authorized_keys admin@server:/root/.ssh/authorized_keys

That rule is root access, just spelled differently. Fine for your own admin account that has full sudo anyway (then it's purely a convenience). For a dedicated backup user, lock it down.

Locking it down with rrsync

rsync ships a helper called rrsync (restricted rsync). Since rsync 3.2.4 it's installed as /usr/bin/rrsync on most distros; older Debian packages keep it under /usr/share/doc/rsync/scripts/. It checks the requested command and only allows access below one directory, and optionally read-only.

Pin the backup key to it in ~backup/.ssh/authorized_keys on the server: 

command="sudo -n /usr/bin/rrsync -ro /srv/data",restrict ssh-ed25519 AAAA... backup@nas

and allow only that in sudoers: 

Defaults!/usr/bin/rrsync env_keep += "SSH_ORIGINAL_COMMAND"
backup ALL=(root) NOPASSWD: /usr/bin/rrsync -ro /srv/data

The env_keep line matters: sudo's env_reset strips the environment by default, and rrsync needs SSH_ORIGINAL_COMMAND to know what the client asked for. Without it rrsync just complains that it wasn't started from sshd.

With a forced command= the client's --rsync-path is ignored anyway; sshd runs the forced command and rrsync reads the original request from SSH_ORIGINAL_COMMAND. The client just does: 

rsync -a backup@server:/ ./backup/data/

Paths are now relative to /srv/data, writes are refused, and a stolen backup key can read that one directory and nothing else.

Gotchas worth knowing

  • sudo only covers the remote side. Receiving files locally as a normal user means rsync can't chown them, so -a quietly loses ownership. Either run the local side as root too, or add --fake-super and let rsync store ownership in extended attributes.
  • Local sudo rsync changes your SSH identity. sudo rsync -a ... runs ssh as root, which reads /root/.ssh/ instead of yours and can't see your agent. Point it at your key explicitly with -e "ssh -i /home/you/.ssh/id_ed25519", or preserve SSH_AUTH_SOCK.
  • Use --numeric-ids for backups. Otherwise rsync maps users and groups by name, and www-data on the server may not be the same UID on the backup box.
  • Full fidelity needs -AXH. ACLs, extended attributes and hard links aren't part of -a. For system backups: rsync -aAXH --numeric-ids --rsync-path"sudo -n rsync" ...=

Why this is worth doing

It keeps the rule "nobody logs in as root" intact without making root files unreachable. No extra daemon, no second SSH server, no shared root key sitting on a NAS. One flag on the client, one line in sudoers, and with rrsync a setup where the backup key can do exactly one thing.
