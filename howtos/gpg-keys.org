#+TITLE: What a GPG key is actually good for
#+AUTHOR: Tobias Yang
#+DATE: 2026-08-30

* Why bother with GPG at all

Most people meet GPG once, to encrypt an email nobody else encrypts either,
and never touch it again. That undersells it badly. A single GPG keypair
backs two tools I use daily: a password manager (~pass~) and signed Git
commits. Same key, two very different jobs: one keeps secrets, the other
proves authorship.

* Generating a key

#+BEGIN_SRC bash
gpg --full-generate-key
#+END_SRC

Pick RSA 4096 (or ed25519 if your tooling supports it), a reasonable
expiry (1-2 years, renewable), and a real name + email; the email is the
identifier ~pass~ and Git will both look up later.

List it:

#+BEGIN_SRC bash
gpg --list-secret-keys --keyid-format long
#+END_SRC

* Using it with =pass=

[[https://www.passwordstore.org/][pass]] is "the standard unix password
manager": a thin wrapper around GPG-encrypted text files, versioned with
git. No server, no proprietary format, no vendor lock-in.

#+BEGIN_SRC bash
pass init "your-email@example.com"
pass insert homelab/gitlab-root
pass show homelab/gitlab-root
#+END_SRC

Every entry is one file, encrypted to your GPG key. ~pass show~ decrypts
it on the fly; nothing sits in plaintext on disk. Combine it with
=pass git init= to sync the encrypted store across machines the same way
you'd sync any other git repo.

* Using it for commit signing

Same key, different purpose: proving that a commit actually came from you,
not from someone who pushed under your name.

#+BEGIN_SRC bash
git config --global user.signingkey <KEY-ID>
git config --global commit.gpgsign true
#+END_SRC

From then on every commit gets signed automatically:

#+BEGIN_SRC bash
git commit -m "some change"
git log --show-signature -1
#+END_SRC

GitHub/GitLab show a "Verified" badge once your public key is uploaded to
the platform (Settings → GPG Keys). Export it with:

#+BEGIN_SRC bash
gpg --armor --export <KEY-ID>
#+END_SRC

* Why one key for both

It's not strictly necessary: you could keep a dedicated signing key and
a dedicated encryption key. But for a personal setup, one identity that
both proves "this commit is mine" and "only I can read this secret" is
easier to reason about and easier to back up: one key, one revocation
certificate, one thing to protect.
