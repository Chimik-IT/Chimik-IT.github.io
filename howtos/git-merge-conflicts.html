The problem

Two branches touched the same lines and git can't guess which version you want. It stops mid-merge, drops conflict markers into the affected files, and leaves the working tree in a half-merged state until you resolve it. Panicking or blindly picking "theirs" or "ours" is how you lose changes you actually needed. Reading the markers correctly is the whole skill.

Reading the conflict markers

A conflicted hunk looks like this: 

<<<<<<< HEAD
your current branch's version
=======
the incoming branch's version
>>>>>>> feature-branch

Three things to keep straight:

  • <<<<<<< HEAD down to ====== — what's currently on your branch
  • ====== down to >>>>>>> ... — what's coming in from the branch you're merging
  • The label after >>>>>>> names the incoming branch, so you always know which side is which without guessing

Nothing here is auto-resolved. Both versions are literally in the file, in full — you decide what the final content should be, which might be one side, the other, or a hand-merged combination of both.

Fixing it by hand

Open the file, decide what the merged result should look like, and delete everything you don't want — including the marker lines themselves. <<<<<<<, ======, and >>>>>>> are not valid file content; if any of them survive, you've got a broken file, not a resolved conflict.

Once a file looks right: 

git add path/to/file

git add is also how you tell git "this conflict is resolved" — it's not just for staging new content.

git status as your checklist

Mid-merge, git status lists every file still needing attention under "Unmerged paths". Work through that list; the moment it's empty, git lets you finish: 

git commit

No message needed — git pre-fills one naming the merge, and that's usually fine to keep.

Bailing out instead

If the merge is more trouble than it's worth right now, or you resolved something wrong and want a clean slate: 

git merge --abort

This resets you to exactly where you were before the merge started — no conflict markers, no half-resolved files, no trace of the attempt. Only works while the merge is still in progress, so use it before you commit.

Using vimdiff instead of hand-editing

If you'd rather see both sides lined up than scroll through inline markers, git can hand the conflict to vimdiff directly: 

git mergetool --tool=vimdiff

That opens each conflicted file as a four-way split — your version, the merged result, their version, and the common ancestor — and do=/=dp work the same way they do for any other vimdiff session. Once you save and quit, git treats the file as resolved and stages it for you, so you can skip the manual git add step for that file.

Why the markers are worth understanding directly

Merge tools help, but they're a layer on top of the same three-way markers described above — not a replacement for reading them. A conflict you resolve by understanding what HEAD and the incoming branch actually contain is a conflict you resolve correctly the first time, tool or no tool.
